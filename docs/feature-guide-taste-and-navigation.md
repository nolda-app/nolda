# 구현 지침서 — 취향 분석 · 코스 생성 · 실시간 길안내

이 문서는 **코드를 고칠 사람**을 위한 것입니다. 각 기능이 왜 그렇게 만들어졌는지, 어떤 값을 건드리면 무엇이 달라지는지, 그리고 이미 한 번 밟은 지뢰가 어디인지를 적었습니다.

서비스가 사용자 입장에서 어떻게 흘러가는지는 [서비스 흐름](service-flow.md)을 보세요.

## 1. 전체 구조

```
[사진첩]  ──→ EXIF 추출 + 512px 축소 ──┐
 (브라우저)    photoMeta.ts             │
                                       ├──→ POST /taste/analyze
[유튜브]  ──→ OAuth → 좋아요·구독 집계 ──┘         taste.py
 (구글)        youtube.py                            │
                                                     │  ① Vision으로 사진 읽기
                                                     │  ② 코드가 0.6:0.4로 가중 합산
                                                     │  ③ LLM이 질문 주제·설명 생성
                                                     ▼
                                              [취향 요약 화면]
                                                     │  사용자가 값을 고치고 확정
                                                     ▼
                                              POST /courses
                                                courses.py
                                                     │  후보 장소 안에서만 LLM이 코스 생성
                                                     │  서버가 시간·예산·거리 검증
                                                     ▼
                                              [코스 목록 → 코스 시작]
                                                     │
                                              POST /walk ──→ TMAP 보행자 경로
                                                walk.py         + 회전 안내
```

### 파일 지도

| 파일 | 역할 |
|---|---|
| `backend/taste.py` | 사진 Vision 분석, 가중 합산, 질문 주제 생성 |
| `backend/youtube.py` | 구글 OAuth, 좋아요·구독 수집, 키워드 규칙 점수 |
| `backend/courses.py` | 코스 생성 프롬프트, 서버 검증, 체류 시간 배분 |
| `backend/walk.py` | TMAP 보행자 경로, 회전 안내, 캐시·한도 관리 |
| `backend/places.py` | 후보 장소 로딩 (동네 반경 기준) |
| `frontend/src/planner/photoMeta.ts` | EXIF 추출, 이미지 축소, 못 읽는 형식 걸러내기 |
| `frontend/src/planner/logic.ts` | 서버 결과 → 화면 모델, 폴백, 코스 점수 계산 |
| `frontend/src/planner/LiveCourse.tsx` | 코스 시작 화면, 실시간 위치, 길안내 |
| `frontend/src/planner/NaverMap.tsx` | 네이버 지도 래퍼 |

## 2. 취향 분석 (`taste.py`)

### 설계 원칙

> **숫자는 코드가 정하고, 문장은 LLM이 만든다.**

이 원칙이 이 모듈의 전부입니다. 처음에는 사진 데이터와 유튜브 데이터를 JSON으로 나란히 넘기고 프롬프트에 "사진 6 : 유튜브 4"라고 적어두기만 했는데, 그러면 **사진 2장이 유튜브 200개를 무조건 이깁니다.** 6:4라는 숫자가 실제로는 아무 역할도 하지 않았습니다.

지금은 서버가 직접 계산합니다. LLM은 계산된 값을 **바꾸지 못하고**, 그 값을 설명하는 문장과 질문 주제만 만듭니다.

### 처리 순서

**① 사진 읽기 — `read_photos()`**

고른 사진을 한 번의 Vision 호출에 모두 담아 보냅니다. `detail: "low"`를 쓰면 사진 1장이 약 85토큰이라, 12장을 보내도 1,000토큰 남짓입니다.

사진마다 돌려받는 것: 장소 종류, 태그, 함께 있는 사람 수, 한 줄 설명.
EXIF에서 읽은 촬영 시각과 동네는 **같이 넣어줘서** 판단을 돕습니다.

**② 비율로 변환 — `photo_ratios()` / `yt_ratios()`**

사진과 유튜브를 각각 "항목별 합이 1인 비율"로 바꿉니다. 이게 있어야 비교가 성립합니다. 단위가 다른 두 데이터를 그냥 나란히 놓으면 사과 무게와 오렌지 개수를 비교하는 것과 같습니다.

항목은 다섯 가지입니다.

| 항목 | 사진 | 유튜브 |
|---|:---:|:---:|
| 관심사 (mood) | O | O |
| 메인 코스 (spend) | O | O |
| 활동성 (pace) | O | O |
| 분위기 (crowd) | O | — |
| 시간대 (hour) | O | — |

분위기와 시간대는 유튜브로 알 수 없어서 사진 전용입니다.

**③ 가중 합산 — `blend()`**

```python
사진 가중치   = 0.6 × min(1, 읽은 사진 장수 ÷ PHOTO_FULL)
유튜브 가중치 = 0.4 × min(1, 유튜브 항목 수 ÷ YT_FULL)
```

`min(1, …)` 부분이 핵심입니다. **근거가 적으면 그만큼 가중치를 깎습니다.**

| 사진 | 유튜브 | 사진 가중치 | 유튜브 가중치 | 결과 |
|---|---|---|---|---|
| 2장 | 200개 | 0.12 | 0.4 | 유튜브가 3배 강함 |
| 10장 | 200개 | 0.60 | 0.4 | 사진이 1.5배 강함 |
| 10장 | 5개 | 0.60 | 0.10 | 사진이 6배 강함 |

실제로 이런 뒤집힘이 일어납니다. 사진 3장에서 카페가 67%로 앞서도, 유튜브 200개가 식사 83%를 가리키면 최종은 **식사 65%**입니다.

**④ LLM — `MERGE_PROMPT`**

확정된 값과 근거 자료를 넘기고, 세 가지만 받습니다.
- 이 사람 기록에서만 나올 수 있는 질문 주제 4개
- 계산으로 알 수 없는 일정(plan) · 누구랑(companion)
- 요약 화면 칩 2~3개

근거 문장(`evidence`)은 **LLM이 아니라 서버가** 숫자로 만듭니다 (`evidence_lines()`). 지어낼 여지를 없애기 위해서입니다.

### 조정할 값

`taste.py` 상단 상수 네 개만 바꾸면 됩니다.

```python
PHOTO_WEIGHT, YT_WEIGHT = 0.6, 0.4   # 기본 비중
PHOTO_FULL, YT_FULL = 10, 20         # 가중치 만점에 필요한 근거 양
PHOTO_LIMIT = 12                     # 분석에 쓸 최대 사진 장수 (비용 상한)
```

> **주의:** `PHOTO_FULL`은 반드시 `PHOTO_LIMIT`보다 작아야 합니다. 크면 사진은 영원히 만점을 못 받습니다.

이 값들은 **실제 사용자 데이터 없이 감으로 정한 것**입니다. 써보고 조정해야 합니다.
- 사진을 더 믿고 싶다 → `PHOTO_FULL`을 낮춤 (예: 5)
- 사진을 덜 믿고 싶다 → 올림 (단, 12 미만)

### 질문 주제 — 고정 6 + 동적 4

**고정** (항상 같은 주제): 분위기 · 시간대 · 활동성 · 일정 · 누구랑 · 예산
**동적** (매 분석마다 새로 생성): LLM이 4개

동적 주제는 이 사람 기록에서만 나올 수 있는 문장이어야 합니다. "아침에 걷는 길", "동네 로컬 포인트" 같은 것들입니다.

선택지마다 `mood` / `spend` / `tag` 기본값이 붙습니다. 이게 있어야 **기존 코스 점수 계산과 동네 선정이 그대로 작동합니다.** 라벨은 자유롭게 바뀌어도 내부 값은 고정된 어휘를 쓰기 때문입니다.

프론트에서는 `applyPicks()`(`logic.ts`)가 사용자가 고른 선택지에서 이 기본값을 꺼내 `taste.mood` / `taste.spend` / `tags`로 만들고, 고른 라벨 문장 자체는 `picked[]`로 코스 생성 프롬프트에 넘깁니다.

### 실패 처리 — 두 갈래가 서로를 막지 않게

사진 읽기와 유튜브 집계는 **독립적으로 실패할 수 있어야 합니다.**

```python
try:
    rows = read_photos(thin(req.photos))
except TasteError as e:
    rows, photo_error = [], str(e)   # 사진만 버리고 유튜브로 계속
```

예전에는 Vision 단계 예외가 전체를 502로 끝냈습니다. 유튜브 데이터가 멀쩡히 있는데도 못 쓰고, 화면은 가짜 데이터로 폴백했습니다. 지금은 사진만 버리고 진행하며, 못 읽었다는 사실을 응답에 실어 화면에 표시합니다.

**양쪽 다 근거가 없을 때만** `TasteError`를 던집니다.

## 3. 사진 처리 (`photoMeta.ts`)

### 무엇을 보내나

원본을 보내지 않습니다. 브라우저에서 **긴 변 512px, JPEG 품질 0.7**로 줄인 뒤 base64로 보냅니다. Vision의 `detail: "low"`가 보는 해상도에 맞춘 값입니다.

EXIF에서는 `DateTimeOriginal`(촬영 시각)과 GPS 좌표만 읽습니다. 촬영 시각이 없으면 파일 수정 시각으로 대신하는데, 이건 정확하지 않습니다 (내려받은 시각이 될 수 있음).

### 못 읽는 형식은 고르는 시점에 걸러낸다

**아이폰 HEIC는 크롬·파이어폭스가 디코딩하지 못합니다.** `createImageBitmap`이 실패합니다.

이걸 분석 단계에서 처리하면 사진이 조용히 사라집니다. 화면에는 "12장 분석 중"이라고 떠 있는데 실제로는 0장을 보내게 됩니다. 그래서 **고르는 순간** `keepReadable()`로 검사해서 걸러내고, 몇 장이 빠졌는지 알려줍니다.

iOS Safari에서 `<input accept="image/*">`로 고르면 보통 JPEG로 변환해서 주지만, PC에서 아이폰 사진 폴더를 그대로 올리면 HEIC가 그대로 들어옵니다.

### 개인정보

사진은 **OpenAI로 전송됩니다.** 축소본이 분석 1회에만 쓰이고 서버에 저장되지 않지만, 외부로 나가는 것은 사실입니다.

연결 화면 고지 문구가 이 내용과 일치해야 합니다. 예전 문구는 "사진 원본은 서버로 보내지 않고 메타데이터만 기기 안에서 읽어"였는데, 기능을 붙이면서 사실이 아니게 되어 수정했습니다. **사진 처리 방식을 바꾸면 이 문구도 같이 확인하세요.**

## 4. 코스 생성 (`courses.py`)

### 기본 구조

LLM은 장소를 **지어내지 못합니다.** 후보 장소를 `p1`, `p2` 같은 짧은 ref로 주고, 그 안에서만 고르게 합니다. 없는 ref, 너무 먼 구간, 시간·예산 초과는 서버가 버립니다.

근거 없는 평가 표현(`인기`, `유명`, `맛집`, `한적`, `붐비지`, `웨이팅`)도 프롬프트로 막고 서버에서 한 번 더 거릅니다. 데이터로 확인할 수 없는 말이기 때문입니다.

### 체류 시간 — 종류별 한도

시간 창(예: 15~21시)을 꽉 채우려고 `fill_stays()`가 체류 시간을 비례 확대합니다. 이때 한도가 종류와 무관하게 하나뿐이면 **식당에 3시간이 배정됩니다.** 실제로 "15시에 식당, 다음 일정이 18시"가 나왔습니다.

```python
STAY_RANGE = {
    "식사": (40, 100), "카페": (30, 120), "한잔": (50, 150),
    "체험": (45, 150), "문화": (30, 120), "산책": (20, 90),
}
```

한도까지 늘려도 시간이 남으면 **더 늘리지 않고 코스가 일찍 끝나게 둡니다.** 비현실적인 시간을 적는 것보다 낫다고 판단했습니다.

시간이 남을 때의 올바른 해법은 체류를 늘리는 게 아니라 **장소를 더 넣는 것**입니다. `place_range()`가 "한 곳에 최대한 오래 있어도 못 채우는" 시간이면 최소 장소 수를 올립니다.

```python
PER_PLACE_MAX = 체류 상한 평균 + 이동 15분  # 현재 136분
need = 올림(시간창 분 ÷ PER_PLACE_MAX)
```

여유롭게 6시간이면 2~3곳 → **3~4곳**이 됩니다.

### 같은 종류 연속 금지

```python
NO_REPEAT_ADJACENT = {"식사", "카페", "한잔"}
```

밥 먹고 바로 또 밥, 카페 나와서 또 카페는 이상합니다. 전시 두 곳을 연달아 보는 것(문화)이나 산책은 자연스러워서 뺐습니다.

프롬프트와 서버 양쪽에서 막습니다. 프롬프트만으로는 새어 나옵니다.

### 조정할 값

```python
PLANS = {
    "tight":   ("촘촘하게 여러 곳", 75, (3, 8)),    # (라벨, 1곳당 평균 분, 장소 수 범위)
    "relaxed": ("여유롭게 한 곳에 오래", 120, (2, 5)),
}
STAY_RANGE = {...}      # 종류별 체류 시간
MAX_LEG_M = 2000        # 도보 한 구간 최대 (직선 × 1.3 추정)
N_COURSES, N_REQUEST = 4, 6   # 돌려줄 코스 수 / GPT에 요청할 코스 수
```

`N_REQUEST`가 `N_COURSES`보다 큰 이유는 서버 검증에서 일부가 버려지기 때문입니다. 검증 규칙을 엄격하게 만들었다면 `N_REQUEST`를 올려야 할 수 있습니다.

`STAY_RANGE` 값도 상식 선에서 정한 것입니다. 특히 **카페 최대 120분**(북카페가 아니면 길 수 있음)과 **한잔 최대 150분**(남는 시간을 마지막 순서가 흡수하는 구조라 자주 상한에 붙음)은 이견이 있을 수 있습니다.

## 5. 실시간 길안내 (`walk.py` + `LiveCourse.tsx`)

### TMAP 한도 관리

보행자 경로 API는 무료 한도가 하루 1,000회입니다. 코스를 걷는 동안 실시간으로 부르기 때문에 그냥 두면 금방 넘습니다. 두 가지로 막습니다.

**① 좌표를 격자로 반올림해 캐시**

```python
GRID = 0.0002  # 약 20m
```

20m 안에서 다시 물으면 같은 경로를 재사용합니다. 걸을 때마다 새로 사지 않습니다.

**② 서버가 하루 호출 수를 직접 셈**

```python
DAILY_LIMIT = 800  # 무료 한도 1,000보다 여유 있게
```

넘으면 `straight()` — 직선 거리 안내로 강등합니다. 실패해도 마찬가지입니다. **길안내가 끊기는 것보다 거친 안내라도 나오는 게 낫습니다.**

### 재탐색 조건

프론트(`LiveCourse.tsx`)에서 제어합니다.

```typescript
const OFFROUTE_M = 50    // 경로에서 이만큼 벗어나면 재탐색
const REROUTE_MS = 20000 // 재탐색 최소 간격
```

GPS가 갱신될 때마다 부르면 한도가 바로 날아갑니다. **목적지가 바뀌었을 때는 즉시**, 경로 이탈은 20초 간격으로만 재탐색합니다.

### 안내 문구

TMAP 응답의 `turnType`을 기호와 말로 바꿔서 씁니다 (`TURNS`). 주의할 점:

- **Point feature의 `distance`는 0입니다.** 거리는 LineString 쪽에 있습니다. 화면에 표시하는 "N m 앞"은 내 위치와 안내 지점 사이 거리를 프론트에서 직접 계산한 값입니다.
- 출발 지점(`turnType` 200, 기호 `◉`)은 이미 서 있는 자리라 안내에서 건너뜁니다. 안 그러면 "10m 앞 출발"이라는 이상한 문구가 나옵니다.
- turnType 코드를 잘못 매핑하면 횡단보도가 "도착"으로 표시되는 식의 오류가 납니다. 값을 추가할 때 TMAP 문서를 확인하세요.

### 위치 권한

`navigator.geolocation`은 **보안 컨텍스트에서만** 동작합니다. `localhost`는 되지만 다른 주소는 https가 필요합니다.

PC에서는 GPS가 IP 기반이라 수 km씩 틀립니다. **실제 동작 확인은 휴대폰 + https 배포 환경에서** 해야 합니다.

## 6. 이미 밟은 지뢰

같은 함정에 다시 빠지지 않도록 기록합니다.

### 네이버 지도가 컨테이너 `position`을 덮어쓴다

지도를 초기화하면 라이브러리가 컨테이너의 `position`을 `relative`로 바꿉니다. `inset: 0`만으로 크기를 잡고 있으면 **높이가 0px이 되어 지도가 안 보입니다.**

```css
/* width/height 명시 필수 */
.pl-livemap { position: absolute; inset: 0; width: 100%; height: 100%; }
```

화면은 비어 보이는데 콘솔에는 에러가 없고, DOM에는 마커와 타일이 다 들어있습니다. 원인을 찾기 어려우니 기억해 두세요.

### `useMemo` 없는 객체 리터럴이 지도를 파괴한다

```typescript
// 이렇게 하면 매 렌더마다 새 객체 → builtAll이 계속 재계산 → 지도가 파괴·재생성
const effTaste = { ...taste, mood: derived.mood ?? taste.mood }
```

`LiveCourse`는 GPS가 갱신될 때마다 리렌더됩니다. 위 코드가 있으면 **지도가 초당 몇 번씩 다시 만들어져서** 아무것도 안 보입니다.

코스 객체를 만드는 경로(`builtAll` → `course.items` → `markers`)의 참조 안정성을 깨뜨리지 마세요.

### 가짜 폴백은 조용히 거짓말한다

분석이 실패했을 때 하드코딩된 더미 사진 24장으로 계산해서 결과를 보여주던 코드가 있었습니다. 사용자가 망원 사진을 골라도 "성수 로스터리 단골"이 떴고, **오류 표시도 없었습니다.**

지금은 제거했습니다. 폴백은 유튜브 규칙 기반으로만 하고, 화면에 안내를 띄웁니다.

> 실패했을 때 그럴듯한 가짜를 보여주느니, 실패했다고 말하는 게 낫습니다. 특히 "내 기록으로 취향을 읽어드릴게요"가 서비스의 핵심 약속인 경우에는요.

### uvicorn `--reload`가 좀비 프로세스를 남긴다

Windows에서 `--reload`로 띄우면 종료 후에도 자식 프로세스가 포트를 잡고 있는 경우가 있습니다. 새 서버가 "Uvicorn running"이라고 찍어도 실제로는 옛 코드가 응답합니다. **새 라우트를 추가했는데 404가 나오면** 이걸 의심하세요.

```bash
netstat -ano | grep ":8000"   # 포트를 잡고 있는 PID 확인
```

## 7. 비용

| 항목 | 호출 시점 | 대략 |
|---|---|---|
| Vision (사진 읽기) | 취향 분석 1회 | 최대 12장, `detail: low`로 장당 ~85토큰 |
| 취향 통합 LLM | 취향 분석 1회 | 텍스트 1회 |
| 코스 생성 LLM | 코스 생성 1회 | 후보 장소 목록이 들어가 입력이 큼 |
| TMAP 보행자 경로 | 코스 진행 중 | 하루 800회 상한, 20m 격자 캐시 |

모델은 `gpt-5-mini`입니다. `gpt-5` 계열은 추론 모델이라 `reasoning_effort="minimal"`이 가장 빠릅니다 (망원 테스트 기준 minimal 14.5초 / low 32.5초 / 기본 약 50초, 결과 품질은 비슷).

환경 변수로 바꿀 수 있습니다: `OPENAI_TASTE_MODEL`, `OPENAI_REASONING_EFFORT`, `TMAP_DAILY_LIMIT`.

## 8. API 요약

| 엔드포인트 | 용도 |
|---|---|
| `GET /health` | 상태 확인 |
| `GET /auth/youtube/login` | 구글 로그인으로 리디렉션 |
| `GET /auth/youtube/callback` | 토큰 교환 → 집계 → 프론트로 `?yt=<id>` |
| `GET /youtube/taste/{id}` | 유튜브 집계 결과 |
| `POST /taste/analyze` | 사진 + 유튜브 → 취향 값 · 질문 주제 |
| `POST /courses` | 취향 + 조건 → AI 코스 |
| `POST /walk` | 두 지점 사이 보행자 경로 + 회전 안내 |

유튜브 토큰은 **저장하지 않습니다.** 로그인 → 수집 → 집계 → 토큰 폐기가 한 번에 끝나고, 결과만 메모리에 `result_id`로 보관합니다. 서버를 재시작하면 사라집니다 (추후 Supabase로 교체 예정).
